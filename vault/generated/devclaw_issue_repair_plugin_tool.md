# Спецификация plugin tool `issue_repair` для DevClaw

## 1. Назначение

DevClaw должен экспортировать существующую CLI-команду `devclaw issue_repair` как OpenClaw/DevClaw plugin tool `issue_repair`. Инструмент нужен оркестратору для безопасного восстановления управляемых provider labels из локального runtime source of truth без прямого shell-доступа.

Сейчас DevClaw может рекомендовать команду:

```shell
devclaw issue_repair <issueId> --source local-state --dry-run
```

Однако оркестратор, которому разрешены только DevClaw tools, не может выполнить штатную диагностику или ремонт. Новый tool закрывает этот разрыв, сохраняя локальное состояние источником истины и не предоставляя произвольный доступ к CLI.

## 2. Границы задачи

В рамках последующей реализации требуется только экспорт операции `issue_repair` как plugin tool и необходимая общая обвязка для совместного использования существующей бизнес-логики CLI.

В задачу не входят:

- ремонт каких-либо конкретных issues;
- запуск repair при регистрации tool или в миграции;
- изменение workflow state;
- назначение или изменение уровня worker;
- изменение иной логики DevClaw, не необходимое для контракта `issue_repair`.

В частности, спецификация не предписывает никаких операций над issues `#81` или `#82` и не разрешает переводить их по workflow.

## 3. Публичный контракт tool

Имя tool: `issue_repair`.

Входная схема должна быть публично зарегистрирована и обнаруживаться тем же механизмом, что и схемы остальных DevClaw plugin tools, включая `task_start` и `health`.

```ts
type IssueRepairInput = {
  channelId: string;
  issueId: number;
  source: "local-state";
  dryRun: boolean;
};
```

Параметры:

- `channelId: string` — обязательный непустой идентификатор текущего чата. Используется штатным механизмом DevClaw для однозначного разрешения проекта. Не является именем проекта и не должен позволять обход project mapping.
- `issueId: number` — обязательный целый положительный номер provider issue. Строковое представление числа, дробное число, `0`, отрицательное число, `NaN` и бесконечность недопустимы.
- `source` — обязательный строго валидируемый источник истины. Первая версия поддерживает только литерал `local-state`. Неизвестные значения нельзя молча заменять значением по умолчанию.
- `dryRun: boolean` — обязательный логический признак режима. Значения `"true"`, `"false"`, `0`, `1`, `null` и отсутствие поля недопустимы.

Дополнительные неизвестные поля должны отклоняться, если это соответствует общей политике схем DevClaw; как минимум они не должны влиять на разрешение проекта или семантику ремонта.

## 4. Семантика операции

### 4.1. Режим `dryRun`

При `dryRun: true` операция:

1. разрешает проект и issue;
2. читает локальный runtime source of truth;
3. читает текущее состояние provider labels;
4. вычисляет расхождения и точный план синхронизации;
5. проверяет, каким был бы итоговый integrity status после применения плана;
6. возвращает структурированный результат.

Этот режим никогда не изменяет GitHub/GitLab labels, локальное состояние или иное внешнее состояние. Запись аудита самого вызова допустима, если аудит не является частью runtime state issue и не меняет результат последующего repair.

### 4.2. Фактический repair

При `dryRun: false` операция синхронизирует управляемые provider labels с локальным runtime source of truth. Она должна применить рассчитанный план, затем повторно прочитать или иным надёжным способом проверить фактическое provider state и вернуть итоговый integrity status.

Успешный ответ означает не только то, что запрос к provider был отправлен, но и то, что проверка целостности завершилась однозначно. Повторный вызов с теми же входными данными идемпотентен: если расхождений уже нет, он не создаёт изменений и возвращает целостное состояние.

Repair не изменяет локальный источник истины для подгонки под provider state. Нельзя включать в план unmanaged labels, если действующая доменная логика DevClaw не считает их управляемой проекцией.

## 5. Разрешение проекта и авторизация

Tool обязан использовать тот же доверенный механизм разрешения проекта по `channelId`, который применяют остальные DevClaw tools:

- неизвестный `channelId` возвращает ошибку;
- отсутствие project mapping возвращает ошибку;
- неоднозначное соответствие нескольким проектам возвращает ошибку, а не выбор первого проекта;
- клиент не может передать произвольный repo path, provider или project slug вместо разрешённого проекта;
- issue должен существовать в разрешённом проекте и в поддерживаемом локальном runtime source of truth;
- provider credentials и полномочия берутся только из штатной конфигурации разрешённого проекта;
- операция выполняется лишь в пределах проекта и provider repository, авторизованных для текущего канала.

До изменения provider state должны завершиться валидация входа, разрешение проекта, загрузка локального issue и вычисление полного плана.

## 6. Структурированный результат

Tool возвращает дискриминируемый результат. Поля могут быть расширены общей метаинформацией DevClaw, но обязательная семантика должна соответствовать следующему контракту:

```ts
type IntegrityStatus = "intact" | "drifted" | "unknown";

type LabelDifference = {
  kind: "missing" | "unexpected";
  label: string;
};

type LabelChange = {
  action: "add" | "remove";
  label: string;
};

type IssueRepairSuccess = {
  ok: true;
  project: { slug: string; provider: "github" | "gitlab"; repository: string };
  issue: { id: number; url?: string };
  source: "local-state";
  mode: "dry-run" | "apply";
  differences: LabelDifference[];
  plannedChanges: LabelChange[];
  appliedChanges: LabelChange[];
  integrityStatus: IntegrityStatus;
  message: string;
};

type IssueRepairError = {
  ok: false;
  code: string;
  project?: { slug: string; provider: "github" | "gitlab"; repository: string };
  issue?: { id: number; url?: string };
  source?: string;
  mode?: "dry-run" | "apply";
  differences?: LabelDifference[];
  plannedChanges?: LabelChange[];
  appliedChanges: LabelChange[];
  integrityStatus: "drifted" | "unknown";
  message: string;
  retryable: boolean;
};
```

Требования к значениям:

- `differences` описывает обнаруженное исходное расхождение.
- `plannedChanges` содержит детерминированный полный план до начала записи.
- В режиме `dry-run` поле `appliedChanges` всегда является пустым массивом.
- В режиме `apply` поле `appliedChanges` перечисляет только подтверждённые изменения.
- `integrityStatus` отражает фактическую целостность после операции. Для `dry-run` при наличии плана он остаётся `drifted`, поскольку внешнее состояние не изменилось; диагностическое сообщение может отдельно указать ожидаемый результат применения.
- Если итоговое состояние нельзя проверить, нельзя возвращать `ok: true`; возвращается ошибка с `integrityStatus: "unknown"`.
- `message` — безопасное диагностическое сообщение для человека, не заменяющее машинно-читаемые поля.

Точные имена вложенных типов могут быть согласованы с общими conventions DevClaw, но нельзя исключать перечисленную информацию или заменять её одним текстовым сообщением.

## 7. Ошибки и атомарность результата

Как минимум требуются отдельные стабильные коды для следующих классов ошибок:

- невалидная входная схема;
- неподдерживаемый `source`;
- неизвестный или неоднозначный проект;
- отсутствующий локальный issue;
- отсутствующий provider issue;
- недостаточные provider permissions;
- ошибка чтения или изменения provider;
- конфликт или изменение provider state во время repair;
- невозможность проверить итоговую целостность.

Ошибка должна быть явной и структурированной; нельзя возвращать успешный результат с предупреждением, если операция завершилась частично или её итог неизвестен.

Предпочтительна одна атомарная provider-операция замены набора управляемых labels, если provider API её поддерживает. Если provider допускает только последовательные изменения и ошибка произошла после части записей, tool должен:

1. не скрывать частичное применение;
2. перечислить только подтверждённые изменения в `appliedChanges`;
3. повторно определить фактическое состояние, если это возможно;
4. вернуть `ok: false` и `integrityStatus: "drifted"` либо `"unknown"`;
5. не заявлять об успешном repair до подтверждения целостности.

Такой ответ остаётся однозначной ошибкой, а не «частичным успехом». Повторный вызов должен быть безопасен благодаря идемпотентности доменной операции.

## 8. Единая бизнес-логика для CLI и tool

Plugin tool не должен повторять алгоритм CLI. Существующую бизнес-логику необходимо выделить или использовать как единый сервис/доменную операцию, принимающую типизированный запрос и возвращающую типизированный результат. CLI и plugin adapter выполняют только разбор собственного транспорта, вызов общего сервиса и форматирование результата.

Единая операция должна отвечать за:

- загрузку локального источника истины;
- получение provider state;
- вычисление расхождений и плана;
- применение изменений;
- проверку итоговой целостности;
- классификацию доменных ошибок.

Это предотвращает расхождение семантики CLI и tool, включая поведение `dryRun`, идемпотентность и правила работы с managed labels.

## 9. Аудит и безопасное логирование

Каждый вызов должен создавать аудит-событие штатным механизмом DevClaw. Оно содержит время, идентификатор вызова, разрешённый project slug, provider, repository, issue ID, `source`, режим, итоговый статус, количество расхождений и изменений, стабильный error code при ошибке.

Для фактического repair аудит должен позволять установить запланированные и подтверждённые действия. Для `dry-run` аудит явно отмечает отсутствие изменений.

Запрещено логировать provider tokens, credentials, полные заголовки запросов, секреты конфигурации и иные чувствительные данные. Тексты ошибок provider должны очищаться перед включением в `message` или логи. `channelId` следует логировать только по действующей политике приватности DevClaw, при необходимости в маскированном или хешированном виде.

## 10. Обратная совместимость CLI

Команда `devclaw issue_repair <issueId> --source local-state [--dry-run]` должна остаться доступной. Её документированная семантика, exit codes и пригодный для скриптов вывод не должны ломаться без отдельного решения о несовместимом изменении.

После перехода на общий сервис существующие CLI-тесты должны продолжать проходить. Новые доменные ошибки должны корректно отображаться в прежнюю CLI-модель ошибок и ненулевых exit codes. Добавление plugin tool не должно требовать от текущих пользователей CLI передавать `channelId`, если CLI уже разрешает проект из своего контекста другим штатным способом.

## 11. Примеры вызова

Проверка без изменений:

```json
{
  "channelId": "931077226",
  "issueId": 123,
  "source": "local-state",
  "dryRun": true
}
```

Применение ремонта:

```json
{
  "channelId": "931077226",
  "issueId": 123,
  "source": "local-state",
  "dryRun": false
}
```

Примеры демонстрируют контракт и не являются указанием выполнить операцию над существующим issue.

## 12. Критерии приёмки

Реализация последующей задачи считается принятой, если:

1. `issue_repair` зарегистрирован и обнаруживается как DevClaw plugin tool тем же способом, что остальные tools.
2. Публичная схема помечает `channelId`, `issueId`, `source` и `dryRun` обязательными и строго проверяет их типы и допустимые значения.
3. `source: "local-state"` использует локальный runtime source of truth разрешённого проекта.
4. `dryRun: true` вычисляет расхождения и план, но не изменяет provider labels или локальное состояние.
5. `dryRun: false` синхронизирует managed provider labels и проверяет фактическую целостность после записи.
6. CLI и tool вызывают один сервис/доменную операцию; отдельной копии repair-алгоритма нет.
7. Повторный успешный repair не производит новых изменений.
8. Неизвестный `source`, отсутствующий issue, неоднозначный проект и provider error возвращают явные структурированные ошибки.
9. Частичное изменение или невозможность проверки никогда не выдаются за успех.
10. Результат содержит проект, issue, источник, режим, расхождения, планируемые и выполненные изменения, итоговый integrity status и диагностическое сообщение.
11. Аудит фиксирует вызов и итог без секретов.
12. Существующая CLI-команда сохраняет обратную совместимость.

## 13. Обязательные тестовые сценарии

### Схема и регистрация

- tool присутствует в реестре и discovery output;
- каждый обязательный параметр по отдельности отсутствует;
- неверный тип каждого параметра;
- пустой `channelId`;
- нулевой, отрицательный, дробный и строковый `issueId`;
- неизвестный `source`;
- не-boolean значение `dryRun`.

### Разрешение и права

- канал однозначно разрешается в проект;
- неизвестный канал;
- отсутствующий project mapping;
- неоднозначный project mapping;
- issue отсутствует в локальном состоянии;
- issue отсутствует у provider;
- issue или repository не принадлежит разрешённому проекту;
- provider credentials не имеют требуемых прав.

### `dryRun`

- состояние уже целостно: пустые `differences`, `plannedChanges` и `appliedChanges`, статус `intact`;
- обнаружены отсутствующие и лишние managed labels: возвращён детерминированный план, статус `drifted`;
- после вызова provider labels и локальные файлы побайтно/семантически не изменились;
- provider read error возвращает структурированную ошибку.

### Применение

- добавление отсутствующих managed labels;
- удаление неожиданных managed labels без удаления unmanaged labels;
- одновременное добавление и удаление;
- подтверждённый итоговый статус `intact` после repair;
- повторный repair возвращает пустой план и не вызывает лишних provider mutations;
- provider write error до изменений;
- provider error после частичного изменения;
- конкурентное изменение labels;
- ошибка контрольного чтения после записи возвращает `ok: false` и `integrityStatus: "unknown"`.

### Общий сервис и совместимость

- contract tests подтверждают одинаковые план и доменный результат для CLI и tool при одинаковом контексте;
- существующие CLI-тесты и exit codes сохраняются;
- audit tests подтверждают поля dry-run, apply, success и error;
- тест логирования подтверждает отсутствие токенов, credentials и необработанных секретов provider.

## 14. Результат текущей документационной задачи

Результатом данной задачи является только этот Markdown-документ. Production code, plugin registration, runtime logic, provider labels, локальное состояние issues и workflow state в её рамках не изменяются.
